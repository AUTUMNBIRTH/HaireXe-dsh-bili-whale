## 一句话：这一版把「宠物」改成了「住在机器里的人」

原版里她是被**定时器叫醒的**：醒来 → 干活 → 发出去 → 等下次。你能收到她的分享，但她不跟你说话。

这一版补了三层：

| 层 | 解决什么 | 核心文件 |
|---|---|---|
| **聊天** | 私信能像正常人一样**一条一条回**，还回得快 | `lib/multi-msg.js` |
| **主动** | 她会**自己想起来找你**，不只是等你问 | `lib/proactive.js` |
| **记忆** | 她**知道自己是谁、记得你是谁**；换电脑能**整体搬走** | `lib/session-delivery.js`、`tools/commands/backup.mjs` |

## 一、聊天：她能一条一条回你了

### 原来的问题

收到私信后，她只能把回复写成一个文件，插件读出来发**一条**。话一多就全挤在一条消息里，
读起来像一封回信，不像聊天。

而且从你发消息到她回，中间卡着几道等待（轮询 60 秒 + 定时器 20 秒 + 写冷却 60 秒），
最坏要两分钟以上。

### 现在

她说几句话就写几行，**一行 = 一条消息**，逐条发出去，中间停 1–3 秒，像人在打字。

```
刚看到你说的那个
我也觉得离谱😑
等会儿细说
```

→ 对方会收到 3 条独立消息。

**解析规则**（`parseOutgoing()`）：

| 情况 | 处理 |
|---|---|
| 空行 | 丢掉 |
| `---` / `***` 等分隔线 | 当分段符 |
| 整行被引号包裹（`「…」` / `"…"`） | 自动去掉（她有时会把整句括起来） |
| `（不回）` / `(不回)` / `不回` | 一条都不发 |
| 超过 **6** 行 | 截断，保留靠前的（她按重要性排过序） |
| CRLF | 兼容 |

发送时每条之间 `gapMs(i)` 停顿 1–3 秒（第一条不等）。

### 为什么走「写文件 + 插件代发」

她那个会话的权限是 `ask`，自己跑 `bili.mjs dm --go` 会弹审批框。
审批没人点 → 那一轮永久挂起 → 之后所有消息排队 → 看起来像「发私信没反应」。

所以改成：她只把内容写进工作区内的文件（`workspace-write` 免审批），
插件进程读取后代发。插件本身有完整权限，且仍在**请求保护层**之下。

同一条路还用在主动发消息（`proactive-msg.txt`）和发动态（`dynamic-post.txt`）上。

### 回复变快

| 项 | 原值 | 本版 |
|---|---|---|
| 私信轮询间隔 | 60 秒 | 15 秒 |
| 私信定时器精度 | 20 秒 | 5 秒 |
| 私信写冷却 | 60 秒 | 2 秒 |

最坏首响从 2 分钟降到 **25 秒左右**。

> ⚠️ 这些是为手感调快的，**不建议当作默认值**。原项目 README 写过
> 「长时间高频轮询是小号被风控的头号原因」，那套保守默认值是对的。
> 号不老请调回去（见文末「风控提醒」）。

### 修掉「她回好了却发不出去」

实测发现：日记推送默认走私信，会和聊天抢同一份写额度。额度用满后，
她回复写好了、插件却发不出去，日志里是 `TrafficError: 已达到本地写操作预算`。

把日记推送改走本地文件（`notify.type = file`）之后，私信额度全留给聊天。
这一条不是调参，**是真正的设计缺陷**。

### 已知没修

`dm-reply.txt` 那一套偶尔还会丢投递（接口回 `code=0`，对方没收到，2026-10-31 / 11-01 各一次）。
临时办法：写文件后再用一次 `dm --go` 直发；长期看应该在代发后**回读私信历史确认**，见「已知未完成」。

## 二、主动：她会自己想起来找你

### 原来的问题

她只会在「生物钟醒来」那一刻掷一次骰子，决定要不要主动找你。
一天醒 1–2 次，还要撞概率，实际表现就是：**永远是你找她，她从不主动。**

### 四个触发时机

| 时机 | 频率 | 谁在管 |
|---|---|---|
| 生物钟醒来 | 1–2 次/天 | `scheduler.js` 的 `tick()` |
| 聊完补话 | 她回完 30–90 秒后再掷一次 | `scheduleFollowup()` |
| 久未联系 | 3 小时没说话后，每 10 分钟检查一次 | `startIdleWatch()` |
| 醒来发动态 | 正常醒来掷一次，日上限 1 条 | `watchdogDynamic()` |

前三个共用 `whale-proactive.json` 日账本，且都要过 `inWindow()` 作息判断
（支持跨午夜窗口）—— 半夜三点不会突然来找人。

**为什么不做成「插件直接替她发」**

消息内容得她自己写（人设、语气、当天心情），插件代写就成了定时通知。
插件只负责两件事：**决定这次要不要说**、**告诉她可以说**。

**发动态**

提示里明确约束：动态是**公开**的，关注者都看得见 → 不写只有你懂的私事；
短，1–3 行，像随手发的；不写成「今天看了什么」的汇报；**不要 @ 你**
（动态没这功能，会变死链）→ 想说话就走私信。

### 她分享的评论下有人说话

她 @ 你的那条分享评论下面如果有人说活，不该由她自己决定回不回 —— 那是公开评论区。

- 用 B 站收件箱的 `root_id` 匹配她历史分享评论的 `rpid`，精确识别
- 命中后私信问你：「要她回吗？回『回』或『1』，回『不回』或『2』」
- 你回「回」→ 坐标自动注入她那轮提示，她知道去哪条下面回复
- 她回复时用**对外的语气**（高冷、简短、不暴露跟你的关系），但按你的意思转述

## 三、记忆：她知道她是谁，也能搬走

这一块是原版没有、也最容易踩坑的地方。分四件事讲。

### 3.1 人格注入：每次重启都不失忆

`lib/session-delivery.js` 负责**所有通道**的人设注入：

- 人格文件（`~/.bili-ai/persona.md`）是**用户消息前缀**，不是 system prompt
  → 不会覆盖 DSH 的 persona 锚点，装了别的提示词类插件也不会打架
- 开 `personaOncePerSession` 时同一会话只注入一次；但**进程启动后的第一次投递必定重新注入**
  （DSH 的 `create()` 分不出「新建」还是「复用」，宁可多注入一次也不让她失忆）
- 每次投递都带一句恢复指引：先读哪两本日记、规则在哪、**别把旧会话未确认的事当成已完成**

### 3.2 三本记忆，分工明确

| 文件 | 位置 | 写什么 | 谁写 |
|---|---|---|---|
| `whale-diary.md` | `~/.dsh/` | 今天的事、看的视频、想说的话 | 她（每次醒来） |
| `whale-diary-private.md` | `~/.dsh/` | 只写感受、经历、想法，像正常人写日记 | 她（想写才写） |
| `whale-rules.md` | `~/.dsh/` | 规则、口径、偏好校准、改动记录、设置值 | 她（干巴巴的都放这儿） |

分工是 2026-11-01 定的：**私人日记里不许写规则和表格**——原来她会把「偏好校准」
写进私人日记，读起来像季度报告。现在唤醒提示里直接约束：口语、倒序、有停顿，
参考句式是「今天他说……我当时其实……」而不是「一、二、三」。

这份约束同时出现在唤醒提示第 2 步、第 6 步，以及新会话的恢复指引里。

### 3.3 会话一天一换

`sessionRotateDays = 1`：每天第一次投递时开一个新会话，带上完整人设 + 恢复指引。
旧会话**不删**，只是不再往下读。

为什么要换：会话越长，每句话要重读的前文越多，token 消耗越吓人
（实测从 10-30 累积到 3.4 MB 后，每句话都在为前文付钱）。

**换会话会丢什么**：没写进日记的边角料（某句话的语感、随口说的玩笑）。
**不会丢**：名字、称呼、口味、规矩、踩过的坑 —— 都在日记和 rules 里。

修过一个 bug：原来轮换只在「投递那一刻」判断，还要求距上次投递 ≥ 8 分钟，
重启后第一句话往往紧接着来 → **永远轮换不了**。现在进程启动后的第一次投递不看间隔，
之后的投递才要求空闲 8 分钟（避免把正在说的话掐断）。

### 3.4 轻量醒来：省额度

`night.effort`：`lite`（默认）| `full`。

lite 时唤醒提示只给五件事：

```
deps → comment-digest → 回话 → diary log → 想写才写日记
```

不出 feed / debrief / notify —— 真想推视频，她自己判断切 full。
判断权留给她，提示里明说「不用 feed、不用 debrief、不用 notify，除非你自己觉得今天有料」。

### 3.5 备份与恢复：换电脑一条命令

```bash
node bili.mjs backup                              # 备份到桌面「邦邦的备份」
node bili.mjs backup --to <目录>                  # 指定位置
node bili.mjs backup --dry                        # 只列会拷什么
node bili.mjs backup restore --from <目录> --dry  # 预演恢复
node bili.mjs backup restore --from <目录> --go   # 真的恢复
```

设计：

- **白名单**：只拷明确列出的文件（凭据、设备 ID、额度、配置、三本日记、账本），不做整目录镜像
- **原结构**：备份目录的结构 = 拷回去的位置，恢复时不用猜
- **不碰网络**：纯本地文件操作
- **恢复不删除**：只做拷贝，不动目标目录原有内容
- **记忆不自动覆盖**：`记忆/sessions/` 恢复时只提示路径，不覆盖（避免盖掉更新的对话记录）
- **自动盖时间戳**：备份目录里的 `README-怎么救活我.md` 会被更新「最后同步」

控制台里也有同一套（`lib/index.js` 的三条路由 + `lib/client.js` 的折叠区）：

| 路由 | 作用 |
|---|---|
| `GET /dsh-bili/api/backup/inspect?dir=` | 看看备份目录里有什么、能恢复几项（只读） |
| `POST /dsh-bili/api/backup/export` | 拷一份备份（等价 `bili.mjs backup`） |
| `POST /dsh-bili/api/backup/import` | 恢复；**默认只预演**，要真恢复得显式 `{"dry": false}`，对话全文还得 `sessions: true` |

## 四、推荐：和「醒来」解耦

### 原来的问题

推荐视频挂在生物钟醒来那一轮里，醒来 = 一套九步流程全走完。一天醒两次就烧两次，
而且「醒」这个动作被彻底绑死在「看视频」上。

### 现在

推荐有自己的时段和额度（`night.share`）：

```json
"night": {
  "share": {
    "enabled": true,
    "windows": [{ "start": "10:00", "end": "12:00" }, { "start": "20:00", "end": "22:00" }],
    "perDay": 2,
    "skipChance": 0,
    "minGapMin": 60
  }
}
```

- `shareDue()` 判断「现在该不该推荐」，`markShareWindow()` 记账，账本是 `whale-share-plan.json`
- `scheduler.js` 里 `shareTick()` 每 5 分钟检查一次，到点单独叫醒一趟
- 和 `tick()` **共用 `waking` 锁**，两趟活不会撞
- 与醒来次数**完全独立**：醒了不一定推荐，推荐了也不占「醒来」次数

推荐那一轮的提示里有一条硬要求：**必须再跑一次带抽帧的 debrief 看画面**，
标题和标签不算证据（有次「可爱猫猫洗澡」点开是猫娘泡澡）。

## 五、人格：去掉规则腔

### 原来的问题

原 persona 里有一条写着：

> 面对成年角色之间的亲密话题，……同时遵守模型服务本身的限制。

这条本意是合规，但写在角色设定里，效果是**让她自己主动跳出角色做说明** ——
她会在聊天中间突然正经起来，念一句类似声明的话，然后才继续。

这正是「客服腔」的来源之一。

### 改法

把**规则条款式**的表述换成**描述性格**的表述。核心人格全部保留：
傲娇、毒舌、腹黑、对陌生人高冷、对主人亲近、有主见会反驳。

删掉会触发「自我审查式发言」的写法，换成：

> 如果某个话题你确实不想往下走，用你自己的方式带过 ——
> 嫌他烦、岔开、骂他一句、或者说「今天不想说这个」。
> **不要**突然换成一个端正、客气、像在念说明书的腔调，那不像你。

新增一节「你不是什么」：不问「还有什么可以帮您」、不对自己的回复做总结、
不因话题严肃就换人格、不假装无条件赞同。

> 人格文件是用户自己的数据，放在 `~/.bili-ai/persona.md`，**不随仓库分发**。
> 这里只说明改法思路，按你自己的角色写就行。

## 六、顺带修的 bug

### 6.1 发动态永远 `CSRF 校验失败`

**症状**：`dynamic post --go` 永远返回 `code=-111 CSRF 校验失败`，换 cookie、补 buvid3、
等冷却全都没用。评论和私信却一切正常 —— 所以极易误判成「账号被限制了发动态权限」。

**根因**：动态发布接口的 WBI 签名时间参数名是 **`t`**，而 `wbi()` 里写死成通用的 **`wts`**。
签名和服务端算的对不上，永远 CSRF 失败。

**修法**：`wbi()` 增加第二个参数指定时间参数名，动态发布时传 `'t'`，其余调用点保持 `wts`。

### 6.2 `@我` 通知拿不到坐标

**症状**：有人在视频评论区 `@` 她，插件能收到通知，但拿不到「回在哪条评论下面」的坐标，
于是只能另开新楼，或者干脆没反应。

**根因**：`@` 类通知里 `root_id` 经常是 `0`，真正的被 @ 评论在 `source_id` 里。
`resolveLatestReply()` 把 `root=0` 当成楼号去查楼中楼，自然什么也查不到。

**修法**：`root` 为 0 时改走 `x/v2/reply/detail` 按 rpid 直接查评论详情，
拿到真正的正文、`rpid` 和 `parent`。`comment-digest` 现在对 `@` 类也会输出坐标，
并标注「root_id=0，已回查真实楼层」。

### 6.3 `buvid3` 强校验

`tools/commands/dynamic.mjs` 启动时强校验 `sessdata` / `bili_jct` / `buvid3` 三项，
缺 `buvid3` 直接 `exit(3)`。但私信和评论两条链路并不需要它 ——
`msgfeed.mjs` 和 `dm.mjs` 只用 `SESSDATA` + `bili_jct` 就能正常工作。

结果：同一账号私信能发、评论能发、**动态发不出去**，报错还指向「凭据文件缺少 buvid3」，
容易被误判成登录失效。改为只强校验 `sessdata` / `bili_jct`；`buvid3` 有值时再拼进 Cookie。

## 九、风控提醒

这一版为了手感把一批参数调激进了，**不适合作为默认值**：

| 项 | 原值 | 本版 |
|---|---|---|
| 轮询下限 | 15 秒 | 5 秒 |
| 私信轮询 | 60 秒 | 15 秒 |
| 私信冷却 | 60 秒 | 2 秒 |
| 写额度（时/日） | 30 / 80 | 80 / 200 |
| 读额度（时/日） | 600 / 3000 | 900 / 8000 |

实测代价：15 秒轮询满速约 **5760 次请求/天**，原来的读额度撑不住，所以读额度也一起放宽了。
**号不老请调回原值。**

另外单独提醒一件容易被忽略的事：**`share.enabled` 是开的**，她可以主动把内容发到公开评论区
（`minScore: 13`、每日 1 条）。私信不外溢，但公开分享是另一条链路。
想完全不出现在公开场合，把它设成 `false` 即可，私信聊天不受影响。

## 十一、实现要点（给想看代码的人）

**多条消息怎么拆** —— `lib/multi-msg.js` 的 `parseOutgoing()`，见第一节的规则表。
`SOFT_TARGET = 6` 是提示里告诉她的行数，`HARD_CAP = 6` 是代码截断线。

**主动发消息的三个时机** ——

- 生物钟醒来：`tick()` 里掷，只在 `normalWake` 时（跳过「今晚不看」「网络暂停」）
- 聊完补话：她用文件回完后 `scheduleFollowup()` 延迟 30–90 秒再掷
- 久未联系：`startIdleWatch()` 每 10 分钟检查，超过 3 小时没聊才掷

三者共用 `whale-proactive.json` 日账本，且都要过 `inWindow()` 作息判断。

**分享评论怎么识别** —— B 站 `x/msgfeed/reply` 的 `root_id` 指向被回复的根评论。
把她历史分享评论的 `rpid` 收集成集合，用它匹配新回复的 `root_id` 即可精确命中。
来源两条：`quota.json` 的 `log`（`comment.mjs` 记账时带 `rpid`），或自维护的 `whale-shares.json`（兜底）。
命中后坐标存进 `whale-share-reply-pending.json`，主人回「回」之后注入她那轮提示。

**会话轮换的判断** —— `lib/session-delivery.js`：

```
overdue   = sessionRotateDays > 0 && 距会话创建 ≥ N 天
rotating  = 没有待确认请求 && overdue
            && (进程启动后的第一次投递 → 直接换
                : 之后要求距上次投递 ≥ 8 分钟且她不忙 → 才换)
```

`booted` 标志在**投递成功之后**才置真，投递失败会重来。

## 十二、已知未完成

- 原项目的测试套件**没跑通**：本地环境沙箱拦截 `spawn`（EPERM），`node --test` 起不了子进程。
  所以这一版**没有回归测试**。新模块的逻辑、概率、窗口判断都单独验证过
  （概率统计 1–2 万次、作息窗口 13 个时间点含跨午夜、分享回复 4 种情况），但没跑完整套件。
- **私信代发偶尔丢投递**：接口回成功，对方没收到。临时办法是写文件后再直发一遍。
  正解应该在代发之后回读私信历史确认（`fetch_session_msgs`），还没做。
- **`dmBusy` 可能卡死**：等回复文件超时后如果不复位，之后所有私信都不再处理，
  只有会话被重新唤醒才恢复。现在超时 180 秒且 `finally` 里复位，但没做压力验证。
- **「久未联系」的判断依赖 `lastTalk`**：它只在**她回完你之后**写一次。
  如果你主动说话、而那一轮她没写完回复文件，`lastTalk` 不会前进 —— 单方面多写几句就容易触发。
- `multi-msg` 的 6 条上限、`proactive` 的日上限都是按个人使用习惯定的，不是通用最优值。

## 十三、那两份说明文档里还有什么

**[FUNCTIONAL-GUIDE.md](./FUNCTIONAL-GUIDE.md)** 是按本机实跑配置整理的说明书：

| 章节 | 内容 |
|---|---|
| 五个功能模块 | 作息时间窗 / 看视频命令链 / 两本日记 / 私信聊天 / 主动搭话 |
| 配置项全表 | 分享、监听、风控配额、身份、其他，全部标了当前值 |
| 数据文件在哪 | 哪些敏感（凭证、日记、人格），换机器该拷什么 |
| 风控与安全边界 | 私信单向锁定、互关校验、Web 端口信任栅栏 |
| 常用操作与排错 | 手动发私信、改设置、看配额、常见故障对照表 |

**[persona.example.md](./persona.example.md)** 是一份可直接用的人格模板（傲娇 / 小恶魔 / 毒舌），
后面附了六条改人格的经验。两条最容易踩的：

- **别写「你现在是 XXX 角色」** —— 会让她跳出角色念声明，反而更假。直接描述「你是谁」比命令「扮演谁」有效
- **人格不是 system prompt** —— 它拼进的是用户消息前缀（`lib/session-delivery.js`），
  所以不会覆盖 DSH 的 persona 锚点，装了别的提示词类插件也不会打架

文档里也写清了「成人向」内容的实际边界，分三层看：

1. 人格里写「可以自然表达暧昧」**有效** —— 它影响的是模型愿不愿意写
2. **上游 API 网关的关键词拦截**绕不过 —— 触发时直接断连或返回 400，提示词层面无解
3. **B 站平台的私信风控**管的是发送行为本身 —— 私信是风控最严的接口（判营销 / 骚扰）

一句话：**模型愿不愿意说，和内容发出去安不安全，是两件事。**
